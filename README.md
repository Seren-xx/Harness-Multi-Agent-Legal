## 🎯 项目背景

传统法律 AI 系统面临三大核心痛点：

| 痛点 | 表现 | 本系统解决方案 |
|------|------|----------------|
| **回答缺乏依据** | 模型容易编造法条，缺乏可追溯的证据链 | RAG 检索增强 + 严格引用校验 + 合规审查 |
| **复杂推理困难** | 单一模型难以处理多步骤法律推理 | 多 Agent 协同（Router → 检索 → 生成 → 审查） |
| **长对话信息失真** | 多轮对话上下文膨胀，关键信息丢失 | 语义缓存 + 历史摘要压缩 + Redis 持久化 |

## ✨ 核心特性

### 🔍 智能检索引擎
- **法条级切分**：按章/条层级切分法律文档，确保法条语义完整性
- **混合检索**：BM25 关键词检索 + 向量语义检索，通过 RRF 算法融合排序
- **CrossEncoder 重排**：使用 BGE-Reranker 对候选结果进行精准重排
- **自适应召回**：检索质量不足时自动扩大召回范围，最多重试 2 次

### 🤖 多智能体协同（4 Agent 固定架构）
- **Router Agent**：动态识别问题类型（问候/常识/法律），智能分流
- **Retriever Agent**：调用法条检索工具 + 判例检索工具，返回结构化证据链
- **Generator Agent**：依据证据生成法律意见，内部调用赔偿计算工具 + 引用验证工具
- **Reviewer Agent**：从 6 个维度校验答案质量，启用只读模式（Plan Only），未通过时驱动"检索增强/答案重写"优化闭环

### 🛡️ Harness 工程化
- **工具集规范化**：4 个法律工具（法条检索/判例检索/赔偿计算/引用验证），统一 `ToolResult` 返回格式
- **工具异常重试**：`@tool_retry` 装饰器实现指数退避重试（最多 2 次），失败自动降级
- **消息标准化**：自动清洗消息格式，满足 API 硬性约束
- **异常重试机制**：指数退避重试 + 上下文过长自动压缩 + 跨模型回退
- **权限控制**：审查阶段启用只读模式（Plan Only），防止篡改原始证据
- **证据完整性校验**：Hash 校验确保检索证据未被修改
- **LangSmith 集成**：记录调用链路、工具执行轨迹与耗时指标

## 🚀 快速开始

### 环境要求

- Python 
- Redis 服务（可选，未安装时自动降级为内存存储）
- 智谱AI 和/或 DeepSeek API 密钥

### 安装步骤

**1. 配置 API 密钥**
```bash
# 设置环境变量
export ZHIPUAI_API_KEY="your-zhipuai-api-key"
export DEEPSEEK_API_KEY="your-deepseek-api-key"
export LANGCHAIN_API_KEY="your-langsmith-api-key"  # 可选
```

**2. 准备法律文档**
将 `.docx` 格式的法律文档放入 `data/raw/` 目录。

**3. 构建知识库**
```bash
# 文档解析：Word → Markdown
python word_to_md.py

# 结构化分块：按章/条切分
python hierarchical_chunking.py

# 构建向量库与 BM25 索引
python build_vector_db_ChromaDB.py
```

**4. 启动 Web 界面**
```bash
streamlit run streamlit_ui.py
```

## 📖 模块详解

### 1. 文档解析与智能检索

#### 文档处理流水线
法律文档通常格式复杂、包含大量噪声，部分文档还包含扫描图片。系统采用四级处理流程：

1. **格式转换**：使用 Mammoth 将 Word 文档转为 Markdown，保留标题层级
2. **OCR 文本抽取**：对文档中的扫描图片、截图等嵌入图像进行 OCR 识别，提取其中的文字内容并合并到 Markdown 文本中，确保图片中的法律条文不遗漏
3. **结构规范化**：通过正则表达式统一法律文档格式，将"第X章"转为 `# 第X章`，"第X条"转为 `## 第X条`
4. **噪声清洗**：去除多余空行、零宽字符、HTML 标签等干扰内容

#### 语义级切分
- 按**章/条**层级切分，确保每条法条语义完整
- 使用 `RecursiveCharacterTextSplitter` 进行二次切分，按段落、句子、标点逐级分割
- 设置 500 token 块大小 + 80 token 重叠，避免法条被截断

#### 混合检索策略
系统同时使用两种检索方式，通过 **RRF（倒序秩次融合）** 算法合并结果：

| 检索方式 | 优势 | 适用场景 |
|----------|------|----------|
| **BM25** | 精确匹配关键词 | 法条编号、专业术语 |
| **向量检索** | 语义相似度匹配 | 口语化表达、同义替换 |

检索后使用 **BGE-Reranker** 对候选结果进行精准重排，确保最相关的法条排在前面。

#### 自适应召回
当检索质量低于阈值时，系统自动：
1. 扩大召回范围（从 150 → 200 条）
2. 在检索词后追加"关键 法条"等引导词
3. 最多重试 2 次，避免无限循环

### 2. 多 Agent 协同推理（4 Agent 固定架构）

系统采用 **LangGraph** 构建有状态的多智能体工作流，核心为 4 个 Agent，工具作为 Python 函数在各 Agent 内部调用，流程固定、稳定可控。

#### Router Agent（路由 Agent）
基于规则优先的策略，将用户问题分为三类：

| 类型 | 识别规则 | 处理策略 |
|------|----------|----------|
| **问候** | 包含"你好""谢谢"等，长度 < 20 | 直接回复，不调用大模型 |
| **常识** | 包含"什么是""如何""为什么"等，长度 < 50 | 轻量级回答，200 字以内 |
| **法律** | 其他所有问题 | 进入完整 RAG 流程 |

#### Retriever Agent（检索 Agent）
负责查询扩展与证据检索，内部调用两个工具：

- **查询扩展**：将用户口语转化为专业法律检索词
- **工具1：法条检索** — 执行混合检索（BM25 + 向量 + RRF + CrossEncoder重排），返回结构化证据链
- **工具2：判例检索** — 基于 RAG 检索相关裁判文书，返回真实案例依据
- **质量校验**：对检索结果进行相关性打分（0-1 分），低于阈值时自动扩大召回范围

#### Generator Agent（生成 Agent）
依据检索到的法条证据撰写法律意见，内部调用两个工具：

- **工具3：赔偿计算** — 当检测到赔偿相关关键词时，自动计算赔偿范围和依据
- **工具4：引用验证** — 验证草稿是否正确引用了法条原文，识别缺失和多余的引用

严格遵循以下规则：
- 必须引用证据中的法条原文
- 不得编造任何法条或案例
- 证据不足时明确说明缺失部分
- 支持审查打回后的多轮重写

#### Reviewer Agent（审查 Agent）
从 **6 个维度** 对法律意见进行结构化审查，启用**只读模式（Plan Only）**：

1. **事实匹配性**：答案是否与法条原文一致
2. **法律条款适用性**：引用的法条是否准确适用
3. **推理链条完整性**：逻辑推理是否连贯无跳跃
4. **逻辑无矛盾**：是否存在自相矛盾的表述
5. **格式规范性**：是否符合法律文书规范
6. **风险点遗漏**：是否遗漏重要法律风险

审查结果以 JSON 格式返回，包含置信度评分。未通过时驱动"检索增强/答案重写"优化循环。

#### 备选方案生成
当多次打回仍未通过审查时，系统生成 3 种不同风格的备选方案：
- **严格引用型**：逐条对应法条原文
- **逻辑推理型**：侧重法律适用条件分析
- **风险提示型**：侧重潜在法律风险指出

由审查官再次评估，选择最优方案。

### 3. 多轮对话与上下文压缩

#### 记忆架构
```
┌─────────────────────────────────────┐
│           Redis / 内存存储           │
│  ┌─────────────┐  ┌──────────────┐  │
│  │ 对话历史    │  │ 对话摘要     │  │
│  │ (List)      │  │ (String)     │  │
│  └─────────────┘  └──────────────┘  │
└─────────────────────────────────────┘
```

#### 摘要压缩策略
当对话消息超过 8 条时，系统自动触发压缩：
1. 提取早期对话内容
2. 调用大模型生成简洁摘要（保留关键法律问题和结论）
3. 仅保留最近 2 轮原始对话 + 历史摘要
4. 摘要存储于 Redis，支持服务重启后恢复

#### 上下文构建
每次调用大模型时，系统构建如下上下文：
```
[系统提示词：历史对话摘要]
[最近 N 轮对话原始消息]
[当前用户问题]
```

### 4. Harness 工程化保障

#### 法律工具集（4 个核心工具）
工具作为 Python 函数在各 Agent 内部调用，不依赖大模型动态决策，流程固定稳定：

| 工具 | 所属 Agent | 功能 | 重试策略 |
|------|-----------|------|----------|
| **法条检索** | Retriever | 混合检索（BM25 + 向量 + RRF + 重排） | 指数退避，最多 2 次 |
| **判例检索** | Retriever | 基于 RAG 检索相关裁判文书 | 指数退避，最多 2 次 |
| **赔偿计算** | Generator | 根据法条计算赔偿范围 | 指数退避，最多 2 次 |
| **引用验证** | Generator | 验证草稿是否正确引用法条 | 指数退避，最多 2 次 |

#### 工具结果规范化（ToolResult）
所有工具调用统一封装为 `ToolResult` 对象，包含：
- `tool_name`：工具名称
- `success`：调用是否成功
- `data`：工具返回数据
- `error`：错误信息（失败时）

配合 `@tool_retry` 装饰器，实现自动重试和失败降级。

#### 消息标准化（normalize_messages）
解决多 Agent 系统中消息格式不一致导致的 API 调用失败，满足三条硬性约束：

1. **字段清洗**：去除内部元数据字段（以 `_` 开头的字段），仅保留 OpenAI API 允许的标准字段
2. **Tool Call 补全**：确保每个 `tool_calls` 都有对应的 `tool` 结果消息，缺失时插入占位符
3. **角色合并**：合并连续相同角色的消息，保证 `user/assistant/tool` 严格交替

#### 异常重试机制
采用三层错误恢复策略：

| 错误类型 | 恢复策略 | 重试次数 |
|----------|----------|----------|
| **上下文过长** | 自动压缩历史消息后重试 | 不消耗重试预算 |
| **API 限流/临时错误** | 指数退避重试（2s → 4s → 8s） | 最多 3 次 |
| **模型服务不可用** | 自动回退到备用模型 | 1 次 |

#### 权限控制（EvidenceGuard）
审查阶段启用**只读模式（Plan Only）**，防止审查 Agent 修改原始证据：

- **只读访问**：通过属性装饰器确保只能读取证据内容
- **完整性校验**：使用 Hash 校验验证证据是否被篡改
- **访问日志**：记录所有证据访问行为，便于审计
- **只读 Prompt**：明确指示审查器只能评估，不得修改或补充证据

#### LangSmith 监控
接入 LangSmith 记录：
- 多 Agent 调用链路
- 工具执行轨迹
- 各节点耗时指标
- 错误日志与重试记录

便于调试多 Agent 流程与持续优化系统性能。

## 📊 性能优化

### 检索优化
- **Jieba 分词预处理**：针对中文法律文本优化分词效果
- **RRF 融合算法**：结合 BM25 和向量检索的优势，权重参数设为 60
- **CrossEncoder 重排**：对 Top-K 候选结果进行精准打分，显著提升排序质量

### 推理优化
- **双模型策略**：日常推理使用轻量级 GLM-4-Flash，深度审查使用 DeepSeek
- **温度控制**：律师生成温度 0.1（确保稳定性），审查温度 0（确保一致性）
- **规则优先路由**：问候语和常识问题直接回复，避免不必要的大模型调用

### 记忆优化
- **摘要压缩**：将早期对话压缩为简洁摘要，减少上下文 token 消耗
- **Redis 持久化**：支持服务重启后恢复对话上下文
- **消息数量限制**：默认保留最近 10 条消息 + 历史摘要
