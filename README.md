## 🎯 项目背景

传统"单次检索 → 单次生成"的法律 AI 系统面临四大核心痛点：

| 痛点 | 表现 | 本系统解决方案 |
|------|------|----------------|
| **任务遗漏** | 复杂问题包含多个相互依赖的研究任务，固定流水线只走一条路径，法律争点覆盖不全 | Planner 动态拆解任务并建立依赖关系（Task DAG），独立任务并行执行，缺失信息触发有界重规划补充任务 |
| **证据冲突** | 多源研究结果相互矛盾（如同一部法律命中多个修订版本）未被察觉即被引用 | Blackboard 汇聚所有研究发现，Reviewer/Arbiter 做确定性冲突检测（法条版本冲突）+ LLM 语义矛盾仲裁 |
| **推理链条过长** | "事实 → 规则 → 要件 → 结论"的长链推理压在一次生成中，容易断裂、跳步 | Research（并行取证）→ Analyst（IRAC 分析）→ Reviewer（审查仲裁）分阶段推理，每步产物落盘可审计 |
| **长对话信息失真** | 对话历史与案件研究进度混存，上下文膨胀、关键信息丢失 | 对话记忆与案件状态（Blackboard）分离存储，历史摘要压缩 + Redis 持久化，支持跨轮追问 |

**核心设计观点**：系统的价值不在 Agent 数量，而在于 **4 个 Agent 角色（Planner / Researcher / Analyst / Reviewer）协同完成一个动态任务图** —— 任务由 Planner 按问题动态生成、按依赖并行调度、经共享状态同步、由审查仲裁闭环，而非写死的固定流水线。

## ✨ 核心特性

### 🔍 智能检索引擎（知识基础设施，与 Agent 解耦）

- **法条级切分**：按章/条层级切分法律文档，确保法条语义完整性
- **混合检索**：BM25 关键词检索 + 向量语义检索，通过 RRF 算法融合排序
- **CrossEncoder 重排**：BGE-Reranker 对候选结果精准重排并归一化打分（0~1）
- **来源解析**：从证据自动解析命中的法律名称与版本日期，供冲突检测使用
- **自适应召回**：检索相关性低于阈值时自动扩大召回范围并追加引导词重试，最多 2 次；重试耗尽返回历次最优结果

### 🤖 多智能体协同（4 个 Agent 角色 + 动态任务图）

- **Planner Agent（规划）**：识别案件类型与法律争点，生成带依赖关系的任务 DAG（事实整理 / 法源检索 / 类案研究 / 要件分析）；LLM 规划失败自动回退兜底计划，保证不中断
- **Researcher Agent（研究）**：每轮（wave）取所有"依赖已满足"的任务，线程池并行执行，研究发现带三层来源标签写入 Blackboard；任务失败不阻断流程（缺口交由审查判断）
- **Analyst Agent（分析）**：综合全部研究发现，按 IRAC 结构建立"事实 → 规则 → 要件 → 结论"推理链，每个结论标注来源层级
- **Reviewer / Arbiter Agent（审查仲裁）**：确定性冲突检测（同一部法律命中多个修订版本）+ LLM 语义审查，三态裁决 **PASS / REPLAN / ESCALATE**

### 🗂 案件 Blackboard（共享状态协作）

```
Redis
├── conversation   对话记忆：用户说过什么（List + 摘要压缩）
└── case_state     案件状态：研究到什么程度（Blackboard）
                   facts / tasks / findings / conflicts / decisions / missing_info
```

- Planner 写 tasks；Researcher 写 findings；Reviewer 写 conflicts / decisions
- 每个案件可在工作台"任务看板 / 研究发现 / 冲突裁决"中审计完整研究过程
- Redis 不可用时自动降级为进程内存储

### 🛡️ Harness 工程化

- **工具结果规范化**：统一 `ToolResult` 封装 + `@tool_retry` 指数退避重试
- **三重防失控**：任务级超时 + 研究波次上限 + 重规划预算
- **权限控制**：审查阶段只读模式（Plan Only），EvidenceGuard 提供 Hash 完整性校验与访问日志
- **双模型互备**：阿里百炼 Qwen / DeepSeek 自动回退；JSON 解析失败自动追加修复指令重试
- **LangSmith 集成**：多智能体调用链路与节点耗时追踪

### 🖥️ 可视化与部署

- **Streamlit 工作台（单页）**：对话 + 任务看板 + 研究发现溯源 + 冲突裁决展示，进程内直调工作流，无需单独后端
- **Docker Compose**：app（Streamlit）+ redis 一键编排

## 🚀 快速开始

### 环境要求

- Python 3.10+
- Redis 服务（可选，未安装时自动降级为内存存储）
- 阿里云百炼 和/或 DeepSeek API 密钥（至少一个）

### 安装步骤

**1. 配置 API 密钥**

```bash
git clone https://github.com/Seren-xx/Harness-Multi-Agent-Legal
cd Harness-Multi-Agent-Legal
pip install -r requirements.txt
cp .env.example .env   # 填入 API Key
```

```bash
export DASHSCOPE_API_KEY="your-dashscope-api-key"
export DEEPSEEK_API_KEY="your-deepseek-api-key"
export LANGCHAIN_API_KEY="your-langsmith-api-key"  # 可选
```

**2. 准备法律文档** 将 `.docx` 格式的法律文档放入 `data/raw/` 目录（仓库内置 250+ 部中国现行法律法规）。

**3. 构建知识库**

```bash
python legacy/word_to_md.py                  # 文档解析：Word → Markdown（含图片 OCR）
python legacy/hierarchical_chunking.py       # 结构化分块：按章/条切分
python legacy/build_vector_db_ChromaDB.py    # 知识库构建：向量库 + BM25 索引
```

**4. 启动多智能体系统**

```bash
# 方式一：可视化工作台（推荐）
streamlit run legal_flow/ui/app.py

# 方式二：Docker Compose（工作台 + redis）
docker compose up --build

# 方式三：命令行直接运行
python legal_flow/orchestration/workflow.py
```

## 📖 模块详解

### 1. 文档解析与智能检索

#### 文档处理流水线

法律文档通常格式复杂、包含大量噪声，部分文档还包含扫描图片。系统采用四级处理流程：

1. **格式转换**：使用 Mammoth 将 Word 文档转为 Markdown，保留标题层级与图片位置
2. **OCR 文本抽取**：对文档内嵌图片执行 OCR（RapidOCR），识别文本就地回填到原图片位置，确保图片中的法律条文不遗漏；未安装 OCR 依赖时自动跳过，不影响主流程
3. **结构规范化**：通过正则表达式统一法律文档格式，将"第X章"转为 `# 第X章`，"第X条"转为 `## 第X条`
4. **噪声清洗**：去除多余空行、零宽字符、HTML 锚点标签等干扰内容

#### 语义级切分

- 按章/条层级切分，确保每条法条语义完整
- 使用 RecursiveCharacterTextSplitter 二次切分，按段落、句子、标点逐级分割
- 500 token 块大小 + 80 token 重叠，避免法条被截断

#### 混合检索策略

系统同时使用两种检索方式，通过 **RRF（倒序秩次融合，权重 60）** 算法合并结果：

| 检索方式 | 优势 | 适用场景 |
|---------|------|---------|
| BM25 | 精确匹配关键词 | 法条编号、专业术语 |
| 向量检索 | 语义相似度匹配 | 口语化表达、同义替换 |

检索后使用 BGE-Reranker 对候选结果进行 CrossEncoder 精准重排，分数归一化到 0~1。

#### 自适应召回

检索质量不足时（Top 证据平均相关性 < 阈值 0.6，或结果为空），`search_articles` 自动执行：

- 扩大召回范围（retrieve_k ×1.5、rerank_k ×2）
- 追加"关键 法条"引导词提升关键词匹配
- 最多重试 2 次；重试耗尽返回历次最优结果（弱证据交由 Analyst / Reviewer 判断），仍无可用结果才判定失败

实现位置：`legal_flow/runtime/tools.py`（工具层）。质量信号（CrossEncoder 重排分数）只在检索返回瞬间可得，放在工具层使所有调用方（statute / element 任务）自动受益，Agent 逻辑保持简单；工具异常另由 `@tool_retry` 指数退避重试兜底。

> **与多智能体的关系**：混合检索实现完整保留为知识基础设施，Research Agent 通过 `runtime/tools.py` 调用 —— RAG 服务于 Agent，而非控制整个流程。

### 2. 多智能体协同与任务调度

系统采用 LangGraph 编排，**4 个 Agent 角色协同完成一个动态任务图**：

#### Planner Agent（规划）

不再做简单的"问候/常识/法律"三分流，而是负责整个系统的分工：

```
用户问题 → 识别案件类型 → 识别法律争点 → 生成任务列表 → 判断任务依赖 → 决定哪些任务并行
```

产出的任务类型与依赖规则：

| 任务类型 | 说明 | 依赖 |
|---------|------|------|
| facts | 案件事实整理（LLM 结构化提取当事人/时间线/争议焦点） | 无（可并行） |
| statute | 法源检索（混合检索适用法条） | 无（可并行） |
| precedent | 类案研究（典型案例裁判要点） | 无（可并行） |
| element | 法律要件分析（构成要件逐项对照案件事实） | 依赖 facts + statute |

LLM 规划输出非法（未知类型/不存在的依赖）时自动清洗；规划整体失败时回退兜底计划，保证系统不中断。

#### Task DAG（任务依赖图）

每个任务包含 `task_id / type / dependencies / status / assignee / result / retry_count`。任务图为纯逻辑模块（不依赖 LLM / 检索 / Redis），行为确定、易于调试与验证：

- **依赖校验**：依赖的任务必须存在；Kahn 算法环检测，有环直接拒绝
- **就绪调度**：`pending` 且所有依赖 `done` 的任务进入就绪队列
- **任务追加**：Reviewer 裁决 REPLAN 后，Planner 针对缺失信息补充任务，动态加入图中

#### Researcher Agent（并行研究）

- **波次调度**：每轮（wave）取所有就绪任务，`ThreadPoolExecutor` 并行执行（默认 3 并发）；无依赖任务天然并行，依赖任务（element）等前置完成后再执行
- **按类型分派**：facts/precedent → LLM；statute → 法条检索工具；element → 检索 + LLM 要件归纳
- **失败容错**：任务失败不阻断流程，以"不可用"研究发现记录缺口，由 Reviewer 纳入缺失信息判断（可能触发重规划补任务）
- **发现溯源**：每个研究发现（Finding）携带三层来源标签与命中法律（名称 + 版本日期），写入 Blackboard

#### Analyst Agent（法律分析）

读取 Blackboard 全部研究发现，按 **IRAC 结构**（事实 → 规则 → 要件 → 结论）产出法律分析草稿，每个结论标注来源层级：

| 来源标签 | 可信度 | 含义 |
|---------|--------|------|
| 〔法条原文〕 | 高 | 结论直接来自检索到的条文 |
| 〔检索验证〕 | 中 | 结论由检索证据推理得出 |
| 〔模型知识〕 | 低 | 结论来自模型内部知识，未经检索验证 |

只引用研究中出现的法条，不得编造；证据不足的要点明确写入"待补充信息"；末尾附风险提示。

#### Reviewer / Arbiter Agent（审查仲裁）

不只判断"答案好不好"，还负责裁决研究发现之间的冲突：

- **确定性冲突检测**：同一部法律命中多个修订版本（不同版本日期）→ 法条版本冲突，提示以最新修订版本为准
- **LLM 语义审查**（只读模式）：事实一致性、引用准确性、推理完整性、研究间矛盾、关键信息缺失
- **三态裁决**：

| 裁决 | 条件 | 动作 |
|------|------|------|
| PASS | 审查通过且置信度 ≥ 阈值 | 定稿输出 |
| REPLAN | 有明确缺失信息且未超重规划预算 | 回 Planner 针对性补充研究任务 |
| ESCALATE | 无法通过且无法/无需再规划 | 带风险提示与待补充清单升级输出 |

#### Bounded Replan（有界重规划）

与"检索重试"不同，重规划是任务级闭环：Reviewer 发现关键信息缺失 → Planner 针对性新增研究任务 → 重新研究、分析、审查。重规划次数有预算上限（默认 2 次），超限自动 ESCALATE，杜绝无限循环。

### 3. 案件状态与多轮记忆

#### 记忆架构：对话记忆与案件状态分离

```
┌─────────────────────────────────────────────┐
│              Redis / 内存降级存储              │
│                                             │
│  ┌─────────────────────┐ ┌───────────────┐  │
│  │ 对话记忆（conversation）│ │ 案件状态        │  │
│  │ 用户说过什么           │ │ （case_state）  │  │
│  │ List + 摘要（String） │ │ 研究到什么程度   │  │
│  └─────────────────────┘ └───────────────┘  │
└─────────────────────────────────────────────┘
```

- **对话记忆**：管理用户说过什么，多轮追问的上下文来源
- **案件 Blackboard**：管理案件研究到什么程度（任务 / 发现 / 冲突 / 裁决），按 TTL 过期

#### 摘要压缩策略

当对话消息超过 8 条时自动触发压缩：

- 提取早期对话内容，调用大模型生成简洁摘要（保留关键法律问题和结论）
- 仅保留最近 2 轮原始对话 + 历史摘要
- 摘要存储于 Redis，支持服务重启后恢复

#### 上下文构建

每轮咨询将历史对话摘要 + 最近消息注入 Planner 与 Analyst 的上下文，实现跨轮追问时保持案件背景一致：

```
[历史对话摘要（语义级缓存）]
[最近 N 轮对话原始消息]
[当前用户问题]
```

### 4. Harness 工程化保障

Harness 的职责不是"让模型更聪明"，而是**"让 Agent 团队不会失控"**。

#### 工具结果规范化（ToolResult）

所有工具调用统一封装为 `ToolResult`（tool_name / success / data / error / laws），配合 `@tool_retry` 装饰器实现指数退避重试与失败降级，失败不向上抛异常、不阻断流程。

#### LLM 三层错误恢复

| 错误类型 | 恢复策略 | 重试次数 |
|---------|---------|---------|
| 上下文过长 | 自动压缩历史消息后重试 | 不消耗重试预算 |
| API 限流 / 临时错误 | 指数退避重试（2s → 4s → 8s） | 最多 3 次 |
| 模型服务不可用 | 自动回退到备用模型（阿里百炼 Qwen ⇄ DeepSeek） | 1 次 |

JSON 输出解析失败时自动追加修复指令重试一次，仍失败返回空对象由上层兜底。

#### 超时与预算控制

| 控制项 | 默认值 | 作用 |
|--------|--------|------|
| TASK_TIMEOUT_SECONDS | 120 | 单轮研究整波超时（future 级） |
| MAX_RESEARCH_WAVES | 8 | 研究波次上限（防死循环） |
| MAX_REPLANS | 2 | 有界重规划预算 |

#### 权限控制（EvidenceGuard / 只读审查）

审查阶段启用只读模式（Plan Only），防止审查 Agent 修改原始证据：

- **只读访问**：属性装饰器确保只能读取证据内容
- **完整性校验**：Hash 校验验证证据是否被篡改
- **访问日志**：记录所有证据访问行为，便于审计
- **只读 Prompt**：明确指示审查器只能评估，不得修改或补充证据

#### LangSmith 监控

接入 LangSmith 记录多智能体调用链路、各节点执行轨迹与耗时、错误与重试记录，便于调试多 Agent 流程与持续优化。

## 📊 性能优化

### 检索优化

- **Jieba 分词预处理**：针对中文法律文本优化分词效果
- **RRF 融合算法**：结合 BM25 和向量检索优势，权重参数 60
- **CrossEncoder 重排**：对 Top-K 候选精准打分并归一化，显著提升排序质量

### 调度优化

- **并行执行**：独立任务（事实/法源/类案）同波并行，依赖任务自动串行，缩短整体延迟
- **模型预热**：并行调度前统一预加载向量库 / BM25 / 重排模型，避免多线程竞争初始化
- **懒加载**：torch / modelscope 等重依赖首次调用才加载，加快服务启动
- **聚焦检索**：研究任务只取 Top 少量证据（rerank_k=8），比全局检索更省时省 token

### 推理优化

- **双模型策略**：日常推理用阿里百炼 Qwen，DeepSeek 自动降级备份，互不单点依赖
- **温度控制**：规划 0.2 / 分析 0.1 / 审查 0，兼顾灵活性与一致性
- **兜底计划**：LLM 规划失败自动回退默认任务计划，保证系统不中断
- **问候短路**：问候语规则识别直接回复，不进入工作流

### 记忆优化

- **摘要压缩**：早期对话压缩为简洁摘要，减少上下文 token 消耗
- **Redis 持久化**：对话记忆与案件状态均支持服务重启后恢复
- **案件 TTL**：案件 Blackboard 按天过期，避免状态无限膨胀
